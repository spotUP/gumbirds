### 68k <-> Z80 protocol (from upstream example, matches nullsound design)
- 68k writes one command byte to REG_SOUND (0x320000, u8). Hardware raises Z80 NMI; nullsound reads the byte (port 0x00), dispatches through `cmd_jmptable` in user_commands.s, replies on port 0xC (68k reads REG_SOUND back: reply). Unverified: exact reply byte values.
- Command ids: 0 unused, 1 prepare_for_rom_switch, 2 free (we use stream_stop), 3 reset_driver, then soundtool-generated from `_SND_CMD_BASE_GENERATED` (default 4): music first, then SFX in sample-map order. Generated C macros: `SND_MUSIC_<NAME>`, `SND_SFX_<NAME>`, `SND_NB_MUSIC`, `SND_NB_FX` in build/snd_commands.h (proven output: SND_MUSIC_STARSHIP_BATTLE=4, SND_SFX_LASER=5, SND_SFX_JUMP=6).
- Do not write the same byte twice in a row without the Z80 clearing it; the 68k must not flood (one command per frame max, queue in sound.c).
- BIOS also sends commands 1 and 3 at boot and on soft reset (UNVERIFIED under UniBIOS; test it). We must not reuse ids 1 and 3.

## Architecture
- Z80: nullsound.lib + our `src/sound/user_commands.s` (command table) + generated instruments/NSS per song. Link base `-b DATA=0xf800` (existing rule). SFX = ADPCM-A samples (6 channels; channels 4-5 reserved for SFX), music = FM/SSG from .fur.
- 68k: `src/sound.c/.h` thin glue; no logic in main.c.
- Test hook: a custom command in user_commands.s increments a Z80 RAM counter `snd_cmd_count` (our own symbol, address read from the link map; add `-m` to the sdld call in our Makefile rule only if build.mk map output is missing: UNVERIFIED how to get the map from the existing `%.ihx` rule; otherwise read from `build/user_commands.lst`/`.map`).

## 68k API (src/sound.h)
```
void sound_init(void);            /* reset_driver (cmd 3), clears queue */
void sound_play_sfx(u8 id);       /* id = SND_SFX_* ; queued, 1 byte per vblank */
void sound_music(u8 id);          /* id = SND_MUSIC_* ; restarts */
void sound_stop(void);            /* cmd 2 stream_stop */
void sound_tick(void);            /* called once per frame: pops one queued command to REG_SOUND */
```
Queue (ring, host-tested) lives in src/core/sound_queue.c; only sound_tick touches hardware. Game events call sound_play_sfx from the game-event handler layer, not from core logic.

## Reachability / test plan (headless MAME, SDL_VIDEODRIVER=dummy -video none -sound none, UniBIOS like test-reach)
Checklist:
- S1 host: sound_queue ring (push/pop, overflow drops oldest or newest documented, one per tick).
- S2 build: m1 contains our cmd table (symbol check) and v1 non-zero where samples.inc says.
- S3 reach (one test, through the game entry point): script boots, coin + start, plays until the game raises a real SFX event (laser fire or hit). Asserts: (a) 68k side: `g_sound_sent` counter (u16 in sound.c) incremented and last command equals SND_SFX_*; (b) Z80 received: audiocpu RAM `snd_cmd_count` (our custom counter) equals g_sound_sent minus BIOS commands, address from the link map; (c) YM2610 written: Lua tap on audiocpu io write ports 0x04..0x07 (`install_write_tap`) sees ADPCM-A key-on (reg 0x00 write via port 4/5, bit7 = 0 key on) for the SFX channel after the command, and FM/SSG register writes after sound_music(). Unverified: MAME Lua tap API form on the installed MAME version; fallback is reading ymfm state or sampling `-wavwrite` and checking non-silence.
- S4 music start/stop: sound_music(id) then sound_stop(): key-on writes appear, then key-off writes.
- S5 soft reset: no stuck command byte, driver reset_driver reissued.
Human test (later, cabinet-independent): `make run`, press coin/start, listen for laser and music; PASS = audible SFX on fire, music loops.
